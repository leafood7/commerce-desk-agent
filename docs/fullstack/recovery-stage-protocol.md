# 完整恢复演练：实施前验收标准

2026-10-29。仅本地演示环境，不模拟生产切换、不删除业务数据、不覆盖当前库或数据卷，不调用模型。封存题集不读取。

1. 在当前验收环境增加一组明确标记的演示订单和政策，创建等待补充商品状态的退货流程。恢复已发布配置，不改变其他流程的快照。
2. 确认没有正在执行或排队的任务，复用备份脚本导出SQL和文档，核对34张表逻辑校验及原文件哈希；恢复到随机命名的新库。原备份、失败与日志保留。
3. 恢复应用使用仅授权新库的独立账户、独立文件副本、全新空Chroma目录、独立API/MCP/执行worker。复用本地镜像与只读模型缓存，不复制原向量数据。与当前系统共用本机Docker和MySQL引擎，不称为异机容灾。
4. 从恢复SQL的当前已发布且生效的不可变chunk重建向量，先核对恢复文件与数据库哈希，再验证索引ID和正文一致。不是重新解析原文或改变切块版本。空索引检查、绑定库名与索引地址检查先于写入。
5. 用恢复API登录，核对原run ID、暂停ID、配置快照和待办状态；实际HTTP MCP检索有正确来源、组织隔离有效。原文件可读取，恢复端撤回后来源失效，原环境不受影响。
6. 恢复原流程：补充状态→申请预览→独立审批→模拟受理。角色越权被拒绝；相同继续键重复请求不重复办理；同一申请和受理记录数量准确，实际退款仍false、金额仍未知。
7. 重启仅恢复服务，再读原流程与申请，确认结果保留；原环境的演示流程仍等待补充、没有新申请，业务/文档全表逻辑快照与备份后相同。

报告时间与数量以实测为准。只证明本机、同版本、正常暂停点恢复；不推断生产RTO/RPO、异地安全、运行中崩溃的恰好一次或模型质量。演练完成后停止新建演练服务释放内存，保留恢复库、文件、索引、备份和清单，不做自动删除或提交推送。
