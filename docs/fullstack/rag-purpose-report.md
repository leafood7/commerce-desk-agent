# 第12次精进：从统一分支投影到按任务目的保留证据

日期：2026-10-29。代码目录：`D:\VScodeProgects\commerce-desk-agent`。本轮没有新增付费调用、提交或推送。

## 相比上一阶段的跨越

第11阶段验证了长文档和跨条款补全，但补齐后仍可能混入其他分支。简单地对所有问题再做当前申请分支投影，会删掉规则问答合法需要的原文。本阶段把证据目的显式化，让已有的政策检索入口、明确只读核对和退货办理采用不同组装策略。

不是从零新增两个入口，也不是新增模型意图识别；实际跨越是将入口目的落实为可追溯的证据策略，验证隔离与证据保留的取舍，并接回真实API和界面。

## 做了什么、功能及价值

| 改进 | 针对问题 | 实现价值 |
|---|---|---|
| 目的明确的上下文选择器 | 办理约束被套到所有问题 | 办理保持严格投影，问答保留有效检索原文 |
| 入口绑定目的 | 用户或工具元数据自称目的 | 目的由既有程序入口或受限只读路由决定，外部独立字段不能覆盖 |
| 只读发布与提示 | 申请清单不足被当成问答无依据 | clause_bound只读流程发布真实检索证据，不用整套办理清单拒答该问题 |
| 事实及写入边界 | 有政策就被当作有实际字段或已办成 | 原文、订单事实、资格和审批仍分开；问答不创建申请 |
| 固定证据三策略回放 | 无法区分补检与投影带来的变化 | 720条对照复用相同证据，没有新检索、模型调用或原结果覆盖 |
| 真实页面说明 | 用户不知道何时只检索、何时进Agent | 规则入口提示无需办理；只读依据不再标成当前申请分支约束 |

## 有改善，也有未改善

在180档、引用补全上下文中，5道已确认口径问题的证据命中为：原样4/5、无差别投影3/5、按目的4/5。丢掉的同一道照片规则题在3档×2种上下文里共重复6次，不能当作6个独立问题，更不是6次模型误拒答。

8个明确办理变体中，其他分支原文出现由4/8降到0/8。任务分流同时保留问答证据，并保持办理分支约束。

但办理变体的全套原文仍是0/8，平均覆盖也没有提高。投影不是召回机制，不能把片段变短包装为任务完成度提升。该固定证据单步诊断不包含完整Agent的一次补检、字段核对及审批，不代表所有真实业务都失败或成功。

原有长文矩阵、原始标签及人工复核口径保持不变。新增40个任务是作者明确指定的32个问答与8个办理变体，不是独立评测，也不证明系统能自动理解任意混合自然语言问题。

## 技术与作用

复用已有RAG原文验证与分支投影，在Python中增加程序控制的目的选择。FastAPI两类只读入口固定问答目的，LangGraph保留当前流程目的并在更正后重新组装；MCP仍负责实际工具数据，发布前继续验证来源。Pydantic拒绝额外目的字段，React区分只读检索原文与申请分支原文。离线脚本冻结任务、业务映射及父证据哈希，避免评分答案反向影响检索。

没有新框架、数据库迁移或工具写权限。模型、引用扩展及业务审批的默认开关不变。

## 实际困难与处理

1. 隔离其他分支和保留问答证据有冲突。没有统一放宽引用，而是根据程序入口区分目的；问答原文也不等于可直接作业务结论。
2. 空检索对照包含与语料重合的“不”字，简化索引实际有命中，MySQL检查揭示了错误假设。修改为无重合查询，保留空证据断言，重新检查；不是降低阈值或放宽断言。
3. 只读流程此前可能按申请清单完整性提示不足。新clause_bound只读路径改为实际问答证据及问题边界；旧基线行为保留兼容，没有借此扩展所有任务的自由路由。
4. 指标容易被过度解释。因此同时保留证据新增丢失、办理分支片段、全套覆盖和实际API不建单验证，不报告未测量的回答准确率或线上误拒率。
5. 浏览器初验的简短照片问题在真实重排后没有证据，系统正确说明不足。该失败轨迹保留；最终有证据展示用例改用包含明确质量分支与独立结论条件的问句。这不是召回修复，原简短问句的漏检仍未解决。长文重复上传还触发了内容去重，验收文档改为带唯一标题的独立内容，保留服务去重逻辑。
6. 整套浏览器复验暴露了已有会话恢复用例的异步竞态：未等待会话列表返回便读取选项。失败快照已有对应记录，修复为等待列表具备目标选项后再选择，保留完整受理与恢复断言。另一次直接启动浏览器未配套容器订单清单的批次已停止，最终使用一致数据准备脚本复验；这些失败均单独保留。

## 如果独立实现，容易遇到的难点

最容易把所有问题都套进Agent办理清单，或反过来为了不拒答而给模型全部原文。还需处理上下文来源重新校验、只读标签、旧配置兼容，以及目的字段不能越权。测试中“语义无关”也不保证“检索为空”，必须核对真实返回，而不能假定索引行为。
