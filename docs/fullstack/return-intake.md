# 退货原话澄清与事实边界核对

本轮沿用已实现的售后业务、LangGraph 持久化、MCP 工具、RAG 和审批链，增加 `guided_v3`。不增加模型请求，不改变真实退款或外部受理能力。

## 做成什么

- 用户可输入本次需求和商品状态原话。字面规则仅生成候选，并保留原话、Unicode 码点位置和摘要；候选需明确确认，不能直接用于申请。
- 不确定、假设、冲突或转述不会自动成为“未使用”。明确补充或更正可以解决未知状态；描述变化会使旧确认失效。
- 对实际签收、退款金额、银行到账、激活、会员权益、质检和返券金额分别核对。当前仅实际签收可能来自订单字段，其余明确说明缺少能力。政策相关不等于事实已证实。
- 明确“只查／不要提交”的需求在只读工具后结束，不进入申请确认。申请与附带查询混合时，缺少银行到账字段不阻止其他有效退货申请。
- 管理员可声明政策还要求激活、权益或质检事实；缺少可信字段时停止申请并转人工核实。该标注需要管理员核对原文，不是自动政策理解。
- 只有一个合法动作时直接执行确定规则；多个合法动作才允许进入既有受限模型路径。旧 `observed_v2` 保留。

## 本地演示

管理员在配置版本页面新建草稿，选“原话确认与事实边界核对”，保持规则模式后发布。已有流程继续使用创建时快照。

1. 在退货申请页选择演示订单、商品和适用规则，状态保持未知，原话输入“没用过，只拆了外包装。”，启动 Agent。确认原话后才生成申请预览；仍需确认预览、独立审批和模拟受理。
2. 输入“好像没用过，记不清了。”，系统要求澄清；显式选择未使用并补充后可以继续。若更正为已使用，将按商家规则说明限制。
3. 需求输入“只想知道实际退款金额是多少，不要提交。”。系统说明实际退款金额不可查询，不生成申请确认。
4. 需求输入“申请退货，顺便查一下银行是否到账。”。正常退货可继续预览，到账信息单独说明不可核实。

## 边界与难点

这不是通用自然语言条件理解。字面规则覆盖有限，未覆盖表达仍需人工澄清；明确只读意图也只覆盖列出的模式。额外确认增加交互成本。原话和引用即使存在，也不证明商品真实状态或政策含义正确。

主要实现难点是恢复后的状态一致性：可选描述字段的 `null` 不能覆盖前一轮原话，否则明确补充后仍会反复澄清。候选确认必须同时绑定暂停点和原话摘要，不能复用旧候选或夹带新的申请参数。前端必须回填服务器确认后的状态，避免已确认原话却仍显示旧的未知选项。

新标准先于实现冻结，见 `return-intake-protocol.md` 和 `data/evaluation/return_intake_v1/manifest.json`。保存了上一阶段四个核心文件的完整副本与47个源文件摘要；没有声称保存完整隔离部署。未读取封存最终测试题。结果仅针对作者开发样本，不构成独立盲审或线上准确率。

下一步应在确认本轮业务闭环后，围绕真实业务数据适配选择一个缺失事实，例如质检工单状态：先设计可信字段和状态转换，再通过 MCP 只读工具接入；不要先让模型猜测结论。
