# 请求到业务执行的全链路追踪

## 入口与排查方式

工作台 → 执行追踪。每个已认证请求由服务端生成追踪编号，错误提示附带该编号。可粘贴编号查看一次请求，也可输入流程编号，查找同一退货流程的启动、补充、恢复和状态读取请求。

例如：退货因缺少商品状态暂停，补充后继续。两次HTTP请求各自保留编号，但都关联同一流程；后台调度沿用对应提交请求的编号和上级步骤，不因换进程而断链。

1. 选择最近请求或粘贴追踪编号。
2. 按时间线查看接口、后台调度、Agent、LangGraph节点、MCP客户端与服务端、业务服务和检索。
3. 找到失败步骤，展开错误码、上级步骤及数据库操作统计。MCP重试会形成不同调用步骤。
4. 若业务已经写入，按业务记录核实真实状态，不因追踪缺项重新执行操作。

## 记录范围

- API：方法与路由模板、HTTP状态；不保存查询参数和完整URL中的业务编号。
- Agent：流程节点、完成/暂停/取消/失败状态。取证、回答和审核协作节点同样挂在流程下。
- MCP：客户端调用、服务端处理与业务执行之间的父子关系。仅接受通过认证、且与追踪所属商家及操作者一致的关联；浏览器传入的追踪编号不能覆盖服务端生成值。
- RAG：知识快照、向量召回、BM25融合、重排；保存命中数量和有限来源编号，不保存原文与问题。
- 数据库：在所处步骤记录执行次数、累计耗时与异常次数，不保存SQL语句、参数或结果。这些统计也可能包括系统元数据查询，不等于业务专属SQL数量。
- SSE：公开进度事件携带追踪与步骤编号；订阅请求关联其流程。订阅接口的耗时只表示响应建立，不表示整个流或整个任务的耗时。

父子步骤的时间会重叠，不能直接相加当作端到端耗时。人的等待与恢复分开记录，不算一次持续运行。

## 权限与敏感内容

追踪读取沿用流程的操作者边界：只看当前商家中自己的记录，管理员也不会自动获得其他操作者的请求正文。追踪不保存密码、密钥、令牌、用户提问、模型草稿、完整答案、原文正文或SQL正文。定位编号不构成读取权限。

追踪存储异常只写安全诊断提示，不更改已提交的业务结果。接口未捕获异常返回通用提示及追踪编号，不回显异常正文。

## 接口与实现

- `GET /api/v1/traces?run_id=...&offset=0&limit=20`：个人请求列表，最多50条一页。
- `GET /api/v1/traces/{trace_id}?offset=0&limit=200`：步骤时间线，最多500条一页。
- `X-Trace-ID`、兼容的`X-Request-ID`：请求响应关联编号。
- 内部MCP额外传递`X-Parent-Span-ID`。

实现位于`src/workbench/tracing.py`和`trace_models.py`；使用ContextVar传递执行上下文，MySQL保存请求与步骤，SQLAlchemy事件记录数据库统计。新增迁移`0012_request_traces`，只增加追踪表。后台任务入队时保存请求和上级步骤关联，不把令牌放入追踪。

## 限制

这是当前第一方服务的本地追踪能力，不宣称接入了OpenTelemetry或外部监控平台。每次执行上下文最多保存1000个步骤，来源编号最多40项。步骤完成后才保存；进程突然退出或存储失败可能缺失部分记录，页面会提示不能据此断言业务未执行。旧请求不能凭空补回历史追踪。

本轮集中进行正常、失败、权限隔离、后台执行与浏览器功能检查，没有开展模型效果、性能对比或付费评测。后续向量存储适配可继续复用检索步骤的追踪入口。
