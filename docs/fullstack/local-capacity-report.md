# 本地并发链路小批次

日期：2026-10-29。项目路径 D:\VScodeProgects\commerce-desk-agent。

## 工作、意义与技术

新增 scripts/evaluate_local_capacity.py，在真实Docker验收栈中，同时发起10个订单只读运行和2个文档上传任务。使用httpx asyncio并发、实际MySQL与HTTP MCP、持久化运行/SSE、本地BGE文档索引。2份文档明确标记容量演练并保持未发布，不进入政策证据，不执行催单、退款或其他业务写工具，不调用付费模型。

这补充了单用户功能测试之外的真实排队与并发检查；没有为了展示技术而更换队列或增加Redis。当前后台文档作业依然由SQL租约与单worker执行，并不代表2个worker同时处理。

## 可验证产出

10/10只读运行完成、订单号及事件ID无重复检查通过；2/2文档任务ready且未发布。总批次2.438秒。订单总耗时p50=904.36ms，p95=1114.71ms；首进度事件p50=365.81ms，p95=839.21ms。首事件是队列/进度事件，不是首答案token。p95采用最近秩法，10个样本下接近最慢请求，不是稳定分位估计。

原始逐请求轨迹：work/capacity-v1/traces.json；汇总：summary.json；执行日志：run.log。容器资源限制见compose.acceptance.yaml：API512MiB，MySQL512MiB，Chroma1GiB，MCP3GiB/2CPU，worker2GiB/2CPU，Web128MiB；Windows主机约15.8GiB内存。本批同时运行小文档索引，缓存和模型已热，不能外推到冷启动或长文档。

## 难点与学习

实际难点是公平表述：入队不等于处理完成，首进度不是首字，两个任务同时提交不等于两个worker并行。脚本等待实际ready并确认未发布，逐运行核对真实订单与唯一事件，再报告时间。

如果由你做，需区分客户端并发、服务端并行、队列等待与模型推理时间；建议从10个真实只读请求入手，保留原始时间与结果，再增加持续负载和故障条件。

## 边界与下一步

只跑了一批，文档很小、无模型生成、没有持续压测、强制故障、取消或资源耗尽。不得宣称支持生产并发10、模型吞吐、稳定SLA或统计显著性。演练产生的少量会话和未发布文档保留在演示库，未擅自删除。

下一步针对应用排队/恢复增加持久作业调度与观测，再测试持续负载、取消和资源限制；真实生成模型负载仍须遵守预算。复现命令：.venv/Scripts/python.exe scripts/evaluate_local_capacity.py，使用现有私有验收配置且不打印凭证。
