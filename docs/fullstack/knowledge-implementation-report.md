## 完成到哪里

本批次完成并验证“上传文档 → 独立后台解析/索引 → 管理员发布 → 前端政策查询 → API → 认证 MCP → 真实检索 → 来源展示/原文件下载 → 撤回失效”的本地链路。原订单查询继续通过 MCP 查询 MySQL。它是后续 LangGraph 售后 Agent 的工具和知识底座，当前政策回复仍为原文摘录。

- MCP：独立 Streamable HTTP 服务；四个工具；严格入参、角色范围、组织隔离、5分钟派生凭据、登录退出后撤销、超时及返回检查。
- 文档：TXT/MD/文本PDF/普通DOCX，基础标题/页码/表格行解析；固定和结构两种分块；内容/配置去重；不可变版本；人工发布/撤回；缺失页面确认；失败重试。
- 作业：MySQL 持久队列、原子领取、租约/心跳和失效接管；独立 worker。尚未使用 Redis/Celery。
- RAG：独立 Chroma 服务，固定 BGE 向量模型和重排模型；向量/BM25/RRF/重排；组织和已发布版本过滤；SQL正文为依据；返回前再次核对发布状态及证据。
- 前端：上传、处理状态、发布/撤回、原文下载；SSE执行步骤、政策来源。界面保持薄层，没有扩展复杂业务页面。
- 运行：统一启停 API、前端、MCP、worker、Chroma；识别进程目录及启动时间；共享 MySQL 保留。已实测停止后端口关闭、重新启动及浏览器完整链路。

## 发现、退化和限制

1. **重排有收益也有代价。** 无依据题从4条误召回降至2条，但本机CPU检索中位延迟从约22ms增至约3.4s。40条中位数来自单次交替运行，不是独立性能基准或吞吐压测。
2. **同样35/36掩盖了逐题差异。** vector/hybrid未覆盖混合支付退款变体的指定条款；但返回的券返还资料可能支持部分结论，不能据此直接判定语义回答错误。hybrid_rerank补上该条，却把“企业发票是不是只写公司名字就够”变成空结果；原召回已经含有电子发票资料。这是实际的检索退化，不能只报告总分。
3. **仍有相关但不回答问题的证据。** 黑金会费具体金额、加急批准后几分钟发货，两题仍被重排返回会员/物流片段。相关性评分不能替代答案充分性判断，不能据此承诺金额或时效。
4. **本轮不能比较分块优劣。** 18份短政策在600字配置下每份都只有一个片段，fixed与structural没有形成有辨别力的结构差异。两组相同结果不能证明结构分块更好；这组结果保留为短文档对照。
5. **语义与规模仍待验证。** 未做100文档/一万片段容量验收；未加入复杂扫描件OCR、CPU硬超时、Redis队列、完整OAuth/OIDC或远程生产部署。

## 后续具体措施

优先保留端到端主线，不反复重写基础架构：

1. 做一组公开开发用的长文档：跨段条件、例外、表格和范围冲突均有原文标注。冻结必要条款和段落位置，再比较分块及邻段预算；把当前短文档作为回归，不据其宣称分块提升。
2. 进入新售后LangGraph闭环：意图路由 → 查询订单/检索政策 → 明列已知和未知条件 → 只在证据充分时给出结论 → 用户确认 → 登记申请/等待审批 → 查询真实状态。纯查单直接展示字段，简单知识问题可以只走RAG，不强制所有问题进入多工具循环。
3. 对上述两类无依据金额/时效和企业发票退化题，先验证问题字段与证据充分性约束，并保留“正常问题仍能完成”对照。先不追加多轮自省模型调用，不据本轮开发题结果自动更换默认阈值。
4. 随后接Redis短期会话/缓存、上下文压缩、模型超时重试/费用限额，再完成容器实跑及恢复演练。容量与部署检查必须单独报告，不由配置文件存在代替。
