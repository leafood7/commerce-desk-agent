# CommerceDesk 任务总结写作约定

依据用户2026-10-30最新要求。替代先前“只有较大能力跨越才写总结”的限制。

## 什么时候写，保存在哪里

- 每完成一项独立任务，都要写总结。属于同一任务的补测、措辞和小修，直接补充对应文件，避免把同一工作拆成许多篇。
- 保存到`D:/Obsidian/main/90-Templates/commerce-desk-agent`，使用Markdown。
- 文件名用`数字_这次改动.md`，标题说清相对上一版多了什么。现有1—17篇，下一篇18；写前核对目录。
- 编号代表任务或改动记录，不等于Git发布版本。文档整理可以记录，但要明确没有新增产品能力或性能成绩。
- 用户要求改写旧总结时，直接改原文件，不新建备份。本次1—16篇与导读已原位改写，原始历史资料保留追溯。

## 用什么方式写

先讲具体业务和用户变化，再解释技术。短句、常用词、具体例子；保留必要技术名词，并在首次出现时说明它负责什么。不把文件名、接口名、缩写堆成正文。

每篇回答：

1. 上一版有什么问题，这次跨过哪一步。
2. 做了什么、补充了什么功能。
3. 解决什么问题，有什么实际意义和价值。
4. 有什么可核实结果和产出；实验结果与真实业务效果分开。
5. 用了什么技术，各自负责什么。
6. 实际遇到什么困难，如何处理。
7. 如果用户独立实现，可能在哪里卡住。
8. 还有什么没完成，下一步是什么。

## 结果必须说准确

- 实际遇到的问题与假设学习难点分开。
- 保留关键数字、失败、退化和限制；复杂细节链接到项目报告。
- 测试批次重叠不累加，重复题不算独立样本。格式合法、引用存在、回答正确、任务完成分别说明。
- 不把本地演示写成线上部署，不把模拟受理写成退款，不把字符减少写成实际token节省。
- 历史计划标“当时下一步”，当前安排集中写在目录，避免旧结论误导。
- 不编造线上KPI、阅读效率提升或模型质量收益。保存后检查编号、结构、链接与重复文件。

项目代码仍在`D:/VScodeProgects/commerce-desk-agent`。写总结不会自动授权commit、push或修改业务规则。
