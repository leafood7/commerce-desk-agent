# 持久作业调度与执行租约隔离

日期：2026-10-29。代码实际保存在 D:\VScodeProgects\commerce-desk-agent。本轮目标是本地可交付版本，不购买或部署服务器。

## 做了什么与补充了什么

把Docker工作台的运行执行从Web进程内BackgroundTasks迁移到MySQL持久工作队列。新增RunJob私有模型、0004_run_jobs向前迁移、独立run-worker进程；创建Run/FlowAction与入队在同一事务完成。入队失败时运行、消息和作业一起回滚，不能出现“接口已经接受、实际却没任务”的提交窗口。RunJob对同一run/action有唯一约束，领取使用行锁与条件更新。

执行前从保存的父登录会话哈希重新验证身份、组织、当前角色与过期时间，再创建短期MCP授权。队列没有保存明文Bearer或模型密钥。注销或授权过期的作业不调用工具；重新登录后，售后流程即便还没有checkpoint也可以从初始状态恢复。只读查询可重新发起。

引入执行租约、工具前检查、图检查点写入及最终公开发布的租约隔离；统一run→job加锁顺序。租约默认活跃时限120秒加60秒余量，没有实现心跳续约。已开始但失联的作业不会自动接管重放，过期后标为interrupted，交给人工恢复核实。写入仍通过原业务服务、稳定幂等键和真实回执控制，不能撤销已经到达业务服务的操作。

Compose明确采用worker模式，并新增256MiB的run-worker；原worker只负责文档索引。主机旧启动方式保留inline兼容模式，不冒充持久队列。工作台运行策略显示当前实际模式。同步模式用于兼容，不是本次推荐的演示部署。

补充真实容器的“停止执行worker→入队→重启API→恢复worker→只执行一次”和“排队取消不执行”验证；更新本地交付入口README与dispatch.md，删除其中过时的“尚未接入RAG/没有Docker”描述。更新容量脚本支持独立输出目录并拒绝覆盖旧实验。

## 意义、价值与针对解决的问题

解决API进程重启导致已接受任务缺少执行载体的问题，同时避免用自动重试掩盖不确定写入。任务受理、领取、授权、执行、状态发布现在有可核对的持久边界。它是现有Agent链路的后端工程升级，不是添加商城页面或真实退款功能。

技术：SQLAlchemy事务、MySQL行锁/条件更新/唯一约束、Alembic增量迁移、LangGraph检查点与中断恢复、MCP短期委托授权、Docker独立进程、pytest/Playwright故障演练。没有新增Redis、Celery或事件总线；没有将自研SQL队列包装成这些技术。

## 实际困难与处理

容器中发现MySQL锁等待：最终发布的外层事务已锁Run，旧引用验证又打开新事务，并因租约隔离再次申请同一Run锁，形成自等待。SQLite的FOR UPDATE行为不同，早期单元测试没有暴露。修复为在同一事务内做发布引用校验，并补正常办理终态回归。初次容器验收是4通过1失败，失败日志保留；最终API5/浏览器12全部通过后才交付。

另一难点是租约失效后的迟到写入：只在worker领取时检查不够，旧执行仍可能提交图状态。因此检查点与公开发布也受同一租约校验，且避免在网络调用期间长期持有事务锁。该机制仍不能撤销服务端已经提交的业务操作，幂等不是可省略的附加项。

## 如果由你实现，会遇到什么困难

你需要区分“HTTP返回成功”“任务已入队”“worker领取”“业务已提交”和“结果已发布”；处理API重启与worker失联是不同问题。认证不能简单把明文token塞进队列，也不能用worker超级权限代替用户权限。LangGraph中断重入还要求动作标识稳定，不能换键盲重发写工具。

建议先画事务和状态边界，再做入队失败、授权失效、写后超时测试；一定在真实MySQL上测行锁，不只靠SQLite。面试可以用本次自等待故障说明为什么实机验证重要，并展示失败记录和针对性回归，避免只讲“用了队列”。
