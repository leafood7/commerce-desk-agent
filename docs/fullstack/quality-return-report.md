# 第10次精进：从单一路径退货到质量问题分支与条件例外证据约束

日期：2026-10-29。代码目录：`D:\VScodeProgects\commerce-desk-agent`。本轮没有 commit、push 或新增付费调用。

## 相对上一阶段的跨越

第9阶段已经有可追溯质检工单，但所有退货仍沿用同一类期限和商品使用要求，而且“质检未通过”不能说明是否确认存在缺陷。本阶段新增显式质量问题退货分支和独立缺陷判定，打通选择分支、等待缺陷记录、重新检索政策、更正预览和原审批链。

另一个跨越是把 RAG 问题从“找到了正确文档”推进到“同一文档内哪些条款属于当前分支”。保留完整来源，同时单独构造当前业务分支可用的原文上下文，避免不同期限、条件和例外相互混用。

## 做了什么、解决什么问题

| 改进 | 价值与功能 |
|---|---|
| 明确的退货分支 | no_reason／quality_issue 随申请持久化；分支与政策不一致时阻止，不自动选择对用户有利的规则 |
| 独立缺陷判定 | 旧的 failed 保持缺陷未知，只有操作人明确登记才能满足质量问题分支；冲突判定拒绝写入 |
| 独立期限及使用条件 | 演示质量分支允许已使用、签收30天内；不延长无理由7天窗口，亦不自动改变其他权利 |
| 多轮更正 | 更正分支及政策后重查事实、清空旧检索上下文并重建预览，不沿用先前例外 |
| 来源约束的条款投影 | 只投影本次已召回且校验过的来源中的管理员绑定原文，保存摘要与位置；空投影不回退无关全文 |
| 同文档 RAG 对照 | 固定本地向量、BM25、融合及重排，分别测召回覆盖与错误分支干扰，不把引用存在当作答案正确 |
| 可见交互 | 前端新增分支选择、缺陷判定、预览分支说明和当前分支原文，配置页可选择并显示实验模式 |

代价与限制明确保留：补检会增加工作量；4条未知事实题补检后都返回政策片段，但实际字段仍不可查。没有生成回答或真实模型对照，不能宣称线上准确率、回答正确率或幻觉率改善。

“错误分支片段”指标检测的是预先标注的完整原文是否出现，并不涵盖所有语义干扰。原始候选和实际上下文完整保留，便于作者参与复核。

## 技术及作用

Pydantic 约束分支与政策契约，保留默认输入序列化兼容；SQLAlchemy/MySQL 新增持久化字段，Alembic 仅做新增迁移；领域服务判断期限、条件和缺陷；MCP 只读查询可信演示记录；LangGraph 处理等待、刷新、更正与重新核对；RAG 使用本地BGE向量和重排、BM25与融合，新增可追溯条款投影；React 展示明确选择和证据；Docker 复核端到端链路。

## 实际困难与处理

1. 单凭质检 failed 无法判断缺陷。没有将历史结果回填，而是新增独立 finding；旧记录继续未知，由操作人明确登记。
2. 同文档版本过滤仍带来另一分支的期限和条件。投影只保留已召回来源中的当前绑定原话，保留原始引用供复查。
3. 投影后完整覆盖仍只有9/20。没有把片段变短描述为召回改善；保留首次失败边界，再单独验证一次补检及其代价。
4. 新增默认分支可能改变既有幂等和预览摘要。普通无理由申请保持旧序列化形状；分支更正则显式保存并重新核对。
5. 期限提示原先写成“无理由窗口”，在质量分支上会误导。改为“当前所选退货分支窗口”并补检查；配置页也补充真实实验模式标签。

## 如果独立实现，容易遇到的难点

最难的是先定义“结论已知”“满足所选规则”和“最终批准”这几种状态，不让一个 failed／passed 布尔含义承担整个业务。检索时还要区分来源权限、文档范围、条款适用和实际事实；评分答案不能进入召回逻辑。状态恢复时需要清掉旧分支上下文，但保留真实写入记录与审批规则。

## 边界和下一步

这里是明确业务分支和管理员映射规则，不是任意自然语言政策的自动推理。没有照片自动判定、真实质检供应商或退款运费结算；订单商品行与数量也不代表单件实物追踪。没有独立盲审、最终人工语义结论或线上 KPI。原封存测试题未读取。
