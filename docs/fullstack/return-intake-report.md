# 第8次精进：从结构化退货到原话澄清与事实边界核对

日期：2026-10-29。代码目录：`D:\VScodeProgects\commerce-desk-agent`。本阶段没有 commit 或 push，没有新增付费调用。

## 相对上一版本的跨越

上一阶段已把模型约束为合法动作建议，并按人工确认的政策绑定收窄检索，但输入仍依赖结构化选项；相关资料能被检索到，也不代表工具知道实际退款、银行到账或激活状态。

本阶段把“用户原话 → 待确认候选 → 有效条件 → 订单及政策核对 → 申请预览”接进持久化 LangGraph 流程，并在输出中区分政策与实际业务字段。由此可以处理原话不确定、前后更正、明确只读以及申请附带不可查问题，而不让模型决定资格或虚构工具能力。

## 做了什么、解决什么问题

| 措施 | 功能和价值 |
|---|---|
| 原话候选及出处 | 保留原话、码点位置和摘要；字面提取不直接变成已满足条件，用户确认后才能继续 |
| 显式澄清与更正 | 不确定或冲突维持未知；最新明确补充可以解决未知，旧候选不能复用 |
| 按所问事实核对 | 实际签收可来自订单字段；退款、到账、激活等当前不可查询，分别说明缺口 |
| 明确只读分支 | “只想知道／不要提交”停在只读核对，不出现建单确认；混合问题保留能完成的申请部分 |
| 政策必需事实声明 | 管理员指定必须核实的字段；缺字段时业务 API 同样阻止确认，不能绕过 Agent 直接办理 |
| 唯一动作走规则 | 只有一个合法动作时不调用模型、不预留模型额度，保留旧版本用于比较 |
| 对应前端 | 新增需求与原话输入、候选确认、事实提示和受控流程版本选择 |

## 技术与作用

使用 Python／Pydantic 校验入参和确认契约，LangGraph 检查点保存候选及最新条件，MCP 传递实际订单和检索结果，现有 RAG 保留政策来源，MySQL JSON 规则增加必需事实声明，React 展示确认与事实边界，SSE 继续显示工具步骤，Docker 验证整条链路。没有引入新的模型调用、数据库迁移或真实退款能力。

## 实际困难与处理

1. 明确补充“未使用”后仍重复澄清。原因是恢复入参中的 `null` 被当成新描述，确认摘要与历史原话不一致。改为仅在提供非空缺字段时更新描述，保留旧原话后重新核对。
2. 原话确认后前端下拉框仍是“未知”，导致预览按钮被当作有未核对改动而禁用。根据服务器保存的预览回填确认后的状态，并用真实浏览器验证按钮可用。
3. 新流程唯一动作的展示与旧测试预期不同。保留旧流程独立用例，新增流程明确展示固定动作不调用模型，不把正常固定动作误称为模型失败回退。

## 如果独立完成，容易遇到的难点

不能只写一个解析函数：还需处理 LangGraph 恢复时的状态覆盖、幂等请求兼容、候选摘要与暂停点绑定、前端旧值同步，以及绕过 Agent 后业务 API 是否仍守住规则。测试要覆盖正常申请和混合任务，避免把更多拒绝当作质量提升。

## 边界与下一步

当前是带出处的字面候选提取，不是通用自然语言理解；只读识别也只覆盖明确模式。原话确认增加一步交互。必需事实由管理员映射，不是模型自动读懂政策；缺失的事实仍未接入真实服务。未重新做真实模型对照，也没有最终人工语义验收结论，不能宣称线上准确率提高。

下一阶段建议优先补一个有业务价值的可信事实闭环：质检工单的创建、处理、结果读取及状态流转。先完成业务 API 和数据模型，再经 MCP 提供只读查询，让 Agent 根据真实质检字段继续办理；同步扩大同文档条件、例外和用户更正的 RAG 对照。业务写入仍保持明确确认与审批，外部处理继续标记模拟。
