## 技术及作用

- Docker Desktop/WSL2：本机Linux引擎。

- Compose：六服务网络、健康依赖、持久卷、资源约束和隔离端口。
- MySQL/Chroma：业务/图状态与向量数据持久化。
- MCP/LangGraph：工具调用、人工确认、审批和恢复链路。
- pytest/HTTPX/Playwright：实际API、浏览器及故障验收。
- PowerShell/Python：分阶段运行、受控恢复和证据保存。

## 实际遇到的困难与处理

1. Docker首次启动需要初始化WSL磁盘与引擎，短时没有命名管道。通过有界探测和日志区分初始化与故障，随后确认引擎就绪。
2. 官方基础镜像认证超时。主机通过现有代理可访问Docker Hub，但构建客户端仍直连。先确认后台手动代理已被识别，再设置客户端进程HTTP_PROXY/HTTPS_PROXY，解决认证请求，未关闭TLS。
3. 首次模型依赖下载及镜像层导出较慢。保留构建日志与缓存，等待实际CPU依赖安装、导出完成，没有把中间进度当成功。
4. 仅验证页面刷新或进程重启不足。增加完整容器重建，实际验证文件、索引和同一暂停点，而非凭架构推断持久化。
5. 验收脚本需要适配Windows：保留本机演示订单manifest，容器浏览器使用可配置地址，避免串到原开发环境。

## 如果我独立做，可能遇到的困难

- 搞不清主机、WSL、容器、Docker后台及构建客户端各自使用哪个代理。应分别检查认证请求、镜像下载和容器内部下载。
- 把容器里的localhost当作另一服务；需要理解Compose服务DNS和内部端口。
- 不知道哪些数据会随容器删除；应画出数据库、上传文件、向量、检查点对应的卷。
- 只测健康接口，不验证真实业务或恢复；应创建带标记的数据，重建后核对同一ID和实际内容。
- 看到测试失败就无限重试；应先确认问题是网络、依赖、权限还是业务断言，保留失败证据。
- 忽视指标口径；镜像共享层、缓存、VHDX长度与实际磁盘分配不能混为一谈。

建议自己复现一次Config→Build→Start→Test，再单独做容器重建与MCP停机恢复，能解释每一步验证了什么。
