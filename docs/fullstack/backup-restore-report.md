## 意义、技术与效果

解决“只有数据卷、没有验证过可恢复备份”的缺口。使用MySQL mysqldump单事务导出、二进制保真读写、表行数/逻辑校验和、文件SHA256、Docker Compose与Python subprocess。导出不把密码放到命令参数或输出，使用容器已有环境；没有模型调用、没有新增业务办理。

真实难点是Windows文本重定向可能改变SQL编码，以及备份文件和数据库版本引用可能不一致。使用原始字节保存SQL，逐个核对版本对应文件；恢复仅允许新建目标，并比较全部表，而不是只检查文件存在。

如果由你实施，难点是区分“文件拷贝成功”与“业务能恢复”、理解一致性快照和写入期间原文件一致性，以及避免把恢复演练做成覆盖生产库。建议从独立空库开始，先验证哈希和数据，再验证应用恢复。

## 边界与下一步

这是本地演示库的逻辑恢复，不是完整灾难恢复验收。备份前后校验仅说明本次观测一致，不能推出任意并发写入下文件和SQL均一致。尚未验证向量索引从零重建、模型权重恢复、恢复库上的应用启动/流程续接、异地保存、加密、保留策略或RPO/RTO。

下一步补向量重建与应用恢复、服务器备份策略；任何覆盖现有库、删除验证库或破坏性迁移须用户决定。复现命令：.venv/Scripts/python.exe scripts/verify_acceptance_backup.py --verify-new-database，每次创建新验证库，不覆盖已有库。
