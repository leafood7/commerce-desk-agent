# 本人队列观测与权限隔离

日期：2026-10-29。项目代码：D:\VScodeProgects\commerce-desk-agent。

## 完成内容与意义

在持久作业调度后继续补只读观测。新增认证接口GET /api/v1/runtime/queue，返回当前账号的queued/running/finished/failed/interrupted/skipped作业数量、最早排队时长、观测时间及最多5条近期失败。工作台“运行策略”新增“我的执行队列”，每5秒刷新；离开页面取消定时器。

解决“只知道请求已受理，看不出在排队还是失败”的可见性问题。数据来自真实SQL作业记录；一次流程的多次继续处理分别计为作业。历史失败不会因恢复而消失，页面提醒以流程当前状态为准。没有为了图表引入新数据库或改变调度策略。

统计同时按Run的organization_id与owner_id过滤，管理员也只查看本人的队列，此入口不是全局运营后台。只选择需要的字段，不返回父登录哈希、租约令牌、模型密钥或原始错误堆栈。POST被拒绝，不能通过观测接口改任务状态。

技术：SQLAlchemy分组/最小时间/限定数量查询、FastAPI认证依赖、React状态与定时清理、TypeScript构建、SQLite/MySQL隔离测试与真实Playwright浏览器。

## 验证与产出

新增的身份隔离测试在SQLite和真实MySQL各通过1项，覆盖匿名访问、同商家不同账号、不同商家、失败记录过滤、白名单字段及禁止写入。前端构建和静态检查通过。最终真实容器API5项通过（36.46秒）、浏览器12项通过（31.2秒），包含运行策略页的本人队列展示。证据在work/queue-observation-v1/container-test.log；不与上一任务重复相加。

新增模型调用0，业务写工具0。没有线上KPI或生产容量结论；该页面提供执行作业的观测快照，不能据此证明worker在线或即时健康。

## 实际困难与用户学习难点

实际难点是“作业状态”和“流程当前状态”不能混为一谈：同一流程可以有一次失败作业及一次成功恢复，不能把历史失败数展示成当前仍失败的流程数。通过文案区分、绑定公开run_id和限制历史条数处理。

如果由你实施，容易只按商家过滤，误把其他客服的记录暴露；也容易直接序列化整个job对象泄露授权字段。建议先写跨用户/跨组织反例，再做字段白名单和页面展示，避免把管理员页面的权限默认复制给客服。
