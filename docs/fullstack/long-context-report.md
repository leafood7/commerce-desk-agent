## 相对原版的改进

原工作台模型不读取全部聊天历史，所以不存在已经实测的“全历史token爆炸”基线。实际问题是两个模型入口各自预检、退货观察直接截短问题/原因/证据，以及缺少受约束的历史导航入口。

本轮新增统一上下文组装器，保完整当前问题、最新结构化条件和必要证据；较早对话按订单隔离、生成带源消息ID的确定性提取摘要。不会调用额外模型总结。快照及预算沿用现有私有SQL表，当前运行/图中的明确条件优先，历史助手结论不能变成银行到账、独立缺陷或审批事实。

交付[使用说明](long-context.md)、[冻结标准](long-context-protocol.md)、[24项场景清单](../../data/evaluation/long_context_v1/cases.json)、统一输入预算、快照、只读API、前端说明卡片和[原始验收证据](long-context-evaluation/coverage-map.json)。旧Streamlit/toolkit没有改造。

## 实现与价值

|改进|解决的问题|实现|
|---|---|---|
|完整必要输入＋统一预算|尾部更正和例外被静默截断|两模型入口均走pack_messages；超限在HTTP前回退现有合法规则|
|当前条件与来源|把历史描述当最新事实|字段值、当前图/输入来源、运行ID；显式未知保留，切单缺省字段清空|
|受限历史导航|跨订单串用、恢复时读取未来消息|同组织/用户/会话/订单、旧运行更正排除、创建时间边界|
|可追溯提取摘要|额外摘要调用、摘要不可核查|80条窗口、4近期单元、12原话摘要，标明截取、覆盖与来源|
|私有版本快照|重启后丢上下文、缓存错误重放|FlowAction私有前缀；指纹含配置/证据；旧未知调用不重发|
|公开说明与隔离|把私有摘要或草稿提前泄露|仅当前条件与安全指标经API/SSE发布，前端显示最近核对信息|

上下文只支持导航，不决定工具入参、资格、金额、批准或写入；旧业务规则和实时核实继续执行。没有引入Redis、额外摘要模型或新数据库。

## 离线对照与不能外推的结论

[输入组装轨迹](long-context-evaluation/assembly-traces.jsonl)与[结果](long-context-evaluation/assembly-summary.json)共6组机械压力输入×3版本=18条；24项场景是开发清单，通过重叠单测/图/数据库检查映射，不是24个人工语义评分样本。

原观察构造在6组中仅1组完整保留本轮要求的任务、原因和证据文本；统一预算与带摘要版本均为5组完整保留，另1组必要输入过大，在调用前拒绝模型路径。该超长样本绕过正常API输入限制，专测适配器防护，不声称实际客户有此长度。拒绝模型不等于判定业务不合格。

这证明被测输入的组装保真与边界，不证明模型语义或业务完成度提升。摘要与无摘要版本本轮同为5组保真，尚未证实摘要带来策略收益。实际旧模型输入原本就不含全历史，新输入可能更大，不能宣传token节省。记录的是保守UTF8上界，不是实付token；没有真实模型的长历史A/B。

当前不会自动从任意旧自由文本提取全部事实，也不会自动把缺省订单、商品状态或审批从上轮带来；不明确时仍需补充。摘要只覆盖有界窗口，完整原文保留在SQL。原跨渠道政策混用和来源摘要遗漏例外的问题未因此消失。

## 实际困难与修复

1. SQLAlchemy的startswith默认会把下划线当LIKE通配符。初次测试发现旧订单更正历史未排除；改为autoescape并补测用户100次继续上限与内部快照不挤占次数，没有放松断言。
2. 加入上下文指纹后原未知请求缓存回归失败。将指纹放进保留的_cache_context，保持原摘要公式与不重放契约，回归通过。
3. 受限执行环境阻塞TestClient启动；定位并停止本轮测试进程，改本机权限运行。首次测试父临时目录未建也保留日志；后续所有临时目录固定D盘。
4. 构建遇到镜像仓库网络超时，沿用既有代理完成。依赖仍来自既有锁文件，未新增项目依赖或删除卷。
5. 首次浏览器测试错误假设刷新仍已登录。按照既有内存登录设计改为重新认证后恢复，没有为过测试改变账号安全策略；原失败记录保留。
