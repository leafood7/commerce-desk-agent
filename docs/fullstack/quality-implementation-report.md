# 第9次精进：从缺失质检字段到可追溯工单与 Agent 等待闭环

日期：2026-10-29。代码保存在 `D:\VScodeProgects\commerce-desk-agent`。本轮没有提交、推送或付费模型调用。

## 相比上一阶段的跨越

第8阶段能够说明质检字段缺失，但不能产生可信业务记录，也无法等待真实状态变化后继续处理。第9阶段新增独立于模型的演示质检工单领域，把人员处理、MCP 只读查询、政策证据、Agent 暂停恢复和退货审批连接起来。

现在可演示：客服提交质检请求 → 独立处理人开始并登记演示结果 → Agent 刷新后重新核对政策 → 用户确认预览 → 进入原有退货审批。工单、结果、资格和审批分别记录，没有把任何一步直接叫作“退货成功”或“退款完成”。

## 做了什么与实现价值

| 改进 | 针对问题 | 功能及效果 |
|---|---|---|
| 质检工单与处理事件 | 工具没有质检事实 | 新增两张表，保存绑定、状态、修订、处理人及事件 |
| 权限、幂等和状态转换 | 重复创建、越权登记或覆盖结果 | 客服创建、审批角色处理、管理员撤销；同键同参数复用、旧修订冲突 |
| 最新工单与数量绑定 | 把其他商品、其他数量或历史结果混用 | 只取同商家、商品行及数量的最新工单；待处理、撤销或不确定结果维持未知 |
| 明确政策质检要求 | 有结果被误当作必须通过 | 分别配置 recorded／passed，原文要求通过才设置该门槛 |
| 原文引用与预览摘要 | 政策无出处或结果变化后继续办理 | 独立质检要求原文可验证、检索、展示；结果修订进入预览摘要，后续阶段重新核对 |
| MCP 只读工具 | 模型自报结果或扩大工具能力 | 固定商品绑定，校验响应；模型没有登记质检或批准工具 |
| Agent 等待与刷新 | 缺字段只能结束，无法继续 | 质检等待不会建退货申请；刷新后重新读取事实与政策，仍保留确认和审批 |
| 可操作前端 | 只有脚本演示、无端到端交互 | 工单创建、处理、结果登记、撤销及流程刷新均可从页面完成 |

## 技术栈及作用

FastAPI/Pydantic 定义业务 API 和严格入参；SQLAlchemy/MySQL 保存工单、事件与修订，使用父记录锁和条件更新控制并发；Alembic 只做新增表迁移；MCP 暴露只读能力；LangGraph 保存质检等待检查点并恢复；RAG 保留原文及政策版本绑定；React 展示角色操作和流程进展；SSE 沿用工具步骤；Docker 验证真实服务链路。

这轮没有再新增通用调度框架、缓存层或模型调用，用现有技术承载新的业务职责。

## 实际遇到的困难

1. 新迁移完成后，服务仍检查旧版本号，首轮测试在启动时失败。同步版本检查和诊断输出后重跑。
2. 原有空库升级／回退测试与“禁止删除质检审计数据”的迁移策略冲突。改为只有两张质检表都为空时允许回退，有业务记录时继续阻止；没有在真实业务库执行回退。
3. 创建工单异步完成前，浏览器脚本读取了空编号。改为等待界面出现已保存的工单。
4. 开始处理后刷新详情会清空旧说明，可能覆盖用户立即输入的新说明。保存及刷新期间禁用相关输入，验证状态更新后再填结果；没有放宽服务端修订或权限检查。

## 如果独立实现，可能遇到的难点

要先定义质检结果的含义和适用对象，不能从 passed 直接推出所有退货都合法。数据库里“有字段”还不够，需考虑最新工单、数量范围、未知结果及撤销。Agent 恢复必须重查事实，前端也需等待异步写入完成。最容易遗漏的是：用户确认预览以后结果又变了，审批和最终提交同样需要重新核对。

## 未完成边界

结果来自操作人登记的隔离演示数据，没有真实仓库、检测仪器或外部供应商证明。订单行及数量不等于单件实物序列号追踪。处理岗位复用审批角色；没有自动催办、通知、分派或 SLA。新规则页面要求选原文，旧规则兼容无独立质检引用；语义仍由管理员核对，程序不自动判断引用是否完整表达全部条件。

这是新增业务闭环的正确性验证，没有新的模型对照或独立人工语义结论，没有线上 KPI。封存最终测试题未读取。
