# 退货业务纵向切片实施报告

日期：2026-10-29。相对上一阶段的跨越：从催单/加急扩展到订单行级退货申请，并贯通实际业务 API、MCP、知识检索、持久化 LangGraph 和 React 操作。

## 实际交付

- 新增 `0007_return_applications`，三个业务表：不可变的商家规则映射、带版本的退货申请、业务事件。当前共32张表，包含31张应用表及1张Alembic版本表。
- 申请包含真实订单行、严格整数数量、原因及用户陈述的商品状态。实际签收缺失时明确未知，不能从 ETA 补成签收。
- 管理员从已发布退货政策选择原文，人工核对适用 SKU、期限和状态条件。程序核对来源版本、内容、有效期和组织范围；不把人工映射冒充自动语义理解。
- 草稿更正递增版本，预览绑定订单事实与证据；确认冻结内容并占用数量。独立审批、模拟提交前分别复查，拒绝越权、过量、旧确认和条件变化。
- 模拟受理有稳定回执；回执与状态同事务，响应丢失可只读核实并恢复。显示商品金额参考值，但实际退款金额未知，真实退款始终未执行。
- MCP 新增检查、草稿、确认、状态和模拟提交工具；不开放审批工具。新工具复用同一领域函数及既有授权、预算与审计。
- LangGraph 基于工具观察补问、更正、核对、等待审批和继续执行；检索必要来源不全时最多补检一次，再不足则不提交。复用已有 SQL 检查点和后台队列，没有另建任务框架。
- React 增加退货操作、原文选择、审批、状态和恢复；退货/催单近期列表分开，会话历史按实际业务打开正确页面。

详细操作、API 和边界见 [returns.md](returns.md)。

## 真实困难与处理

- 首次在受限执行环境跑本机测试，内部连接被阻塞，定位到测试客户端事件循环建立连接的位置。改在允许本机连接的环境重跑，不把超时当业务失败或通过。
- 实现检查发现：若商品不在规则 SKU 白名单中，就不能继续套用该规则的期限或未使用条件来作拒绝断言。已改为缺适用政策并保留针对性测试。
- 新业务共用 `aftersales` 运行类型，旧会话入口会误入催单页面。已增加服务端业务分类和历史界面路由，并补浏览器检查；没有另建会话体系。
- 现有单价缺少优惠分摊等实付事实，无法可靠计算退款。明确将其命名为商品金额参考值，退款金额保持未知，避免为了演示补造财务结论。

## 剩余能力与下一步

完成的是确定性业务闭环和基于工具观察的状态图，**不是已完成模型自主多轮 ReAct**。本图暂不调用模型规划；自然语言自由抽取、多行合并退货、实际质检、运费/优惠分摊、退款执行和真实平台连接器未实现。模拟超时恢复不能直接外推到真实平台。

下一阶段继续“有业务深度的 Agent＋RAG”：先围绕本退货链路接入可校验的模型只读动作/补问决策，保留规则基线；再冻结范围冲突、例外、缺证据与用户更正的开发场景，比较任务完成与错误，避免只把引用覆盖变成漂亮分数。暂缓新增独立可靠性框架与通用反思架构。
