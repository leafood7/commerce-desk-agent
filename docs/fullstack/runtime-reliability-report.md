## 做了什么、补充了什么

新增 ExecutionLimits 与 call_bounded，共用于售后 LangGraph 和普通订单/政策查询。每次活跃处理默认最多120秒、10次工具尝试；用户等待确认/审批时不计时，继续处理时启动新预算。这是每次继续处理的预算，不是跨整个流程的累计时间上限。现有最多100条继续动作约束仍保留。SQL同步操作采用边界检查，不能宣称数据库慢查询会被硬中断。

只对只读工具的超时和暂时不可用额外重试1次，可配置0—2次，退避默认0.5秒；重试计入工具次数与活跃时限。写工具不自动重试；写超时仍保留不确定状态、稳定幂等键及恢复核对。权限、参数、坏响应不重试，防止把所有异常都当网络故障。

前端订单、政策、售后共用订阅器，支持CRLF、多行data、事件去重、Last-Event-ID续订、有限退避、关闭reader及登录失效停止。提前EOF会核对运行快照，仍处理中才续订同一个运行；不会为重连创建新运行。政策结果仍检查后发布，没有为了打字效果公开草稿。

新增“运行策略”页面和认证接口，白名单返回实际识别模式、工具与时间限制、上下文大小，不返回密钥、内部地址、数据库URL或跨用户用量。本页只读；尚未实现可编辑模型参数/业务提示词版本面板，不把展示页面称为配置系统。

镜像的workbench/knowledge依赖与源码分层，实际后续构建日志确认knowledge-deps CACHED；业务源码变动不再必然重装本地模型依赖。镜像、数据卷、构建缓存继续在D盘。

## 意义与实际价值

针对暂时网络错误导致整段业务失败、无限重试、写入重复、前端将断流误认为完成等问题，提供可检查的控制和状态。模型建议不改变确认与审批规则，真实业务回执继续保存。工作台能说明当前采用何种限制，便于演示与排错。

技术包括Python asyncio.wait_for/单调时钟、Pydantic配置边界、LangGraph受限执行、MCP错误分类、SQL状态与幂等、React/TypeScript共享SSE客户端、Playwright故障注入及Docker多阶段缓存。

## 实际困难与处理

真实困难之一是安全重试边界：读与写不能共用“失败就再来”的逻辑。将是否只读绑定工具契约，并保留不确定写入的恢复测试。另一问题是HTTP状态、协议结构与网络失败容易被合并，错误分类必须先区分再决定重试。

前端原先有重复解析逻辑，且正常EOF也可能是断连。统一解析后，通过真实浏览器替换流响应验证恢复，而不是仅检查界面文案。容器复验必须使用最终前后端源码；期间旧镜像启动链路被中止，最终重建及完整验收结果才作为交付证据。

## 如果由你实施，可能的难点

你需要理解asyncio超时只取消客户端等待、不等于服务端撤销写入；理解幂等键与真实回执如何恢复结果；理解SSE游标、网络断开和业务完成是不同状态。建议先故障注入再实现策略，每条失败都核对数据库申请数量和公开事件，而不是只观察聊天回复。
