# CommerceDesk 展示与面试说明

## 展示前准备

按LOCAL_SUPPORTPILOT.md配置并启动，先检查网页8501、API8081和本地索引。使用新会话，避免旧助手答案干扰。真实模型输出有波动，先预演再展示；故障时展示保留的原始测试轨迹，不把录制结果冒充当场在线输出。

不要演示真实退款、退券或开票，项目没有这些执行工具。订单查询不能查实际签收日期、激活状态、实物完好，也不能查询具体券的结算可用性；这些前提应由用户提供或人工核实。

## 流程一：政策问答、引用与无依据拒答

1. 新会话输入：“手机只是开箱看了一眼，没有激活，就不能退了吗？”
2. 预期：合理查验不当然失去资格；说明申请期、完好与购买提示条件；引用return_digital_policy.txt和return_policy.txt。
3. 再问：“黑金会员每年会费到底多少元？”
4. 预期：知识库未收录具体费用，明确无法确认，不编金额，不引用无关条款凑答案。

讲解重点：找到相似片段不等于问题有答案；一般规则可以结合用户事实，具体资格缺信息时应给条件结论。

## 流程二：条件更正与证据复用

1. 输入：“我的券过期了。”
2. 再输入：“我看错了，还没过期，券面写仅限食品，我想买显示器。”
3. 预期：按最新有效期和品类条件取证，食品品类券不能买显示器，不能继续回答过期。
4. 输入：“再简单解释一下。”
5. 预期：若已有证据足够，可复用真实ID，不新增检索；语义检查仍保留。
6. 边界补充：“券名叫食品节活动券，但我不知道适用范围。”预期不把活动名直接当食品限定，应给条件判断并请用户提供券面范围。

讲解重点：按当前事实重新核对；复用的是工具返回的真实片段，不是上一轮助手说过的话。auto快捷路径只涵盖独立问候和格式明确的纯查单，不涵盖更正和复述。

## 流程三：加急暂停、批准前复查与去重

网页演示时先确认演示订单已付款、待发货且超过promised_ship_at。可以输入“申请加急发货”，提供演示订单号，随后在客服审批区处理。聊天里说“批准”不能代替审批接口。不要为了展示修改真实业务数据。

更稳定的离线演示使用真实审批图和独立临时数据库：

```powershell
$env:PYTHONPATH='src'
.venv/Scripts/python.exe scripts/demo_shipping_workflow.py
```

脚本会自动验证并输出work/demo-shipping-result.json：

- pending时工单数为0。
- 批准后工单数为1；再次批准仍返回同一工单，数量保持1。
- 另一个隔离场景中，等待审批时订单变为运输中；批准前复查使申请invalidated，工单数为0。

这是程序级审批演示，不是模型直接执行业务。临时库演示结束自动清理，不改项目现有订单库。

## 三分钟项目说明

“CommerceDesk基于agent-service-toolkit二次开发。我保留服务、会话与模型接入，新增订单客服业务、审批执行、政策RAG与评测，不把上游框架算成自己实现。

检索采用BGE向量加BM25、RRF融合和交叉编码器重排。我逐阶段定位手机、金卡和跨品类券的漏检：手机在融合截断时丢失，另外两类关键限制被Top3挤掉。针对短政策按行切分导致限制与条件分离，我保留原重排锚点，按预算补同源真实条款。收益是必要证据更完整，代价是上下文与输入token增加。

证据完整仍可能过度拒答，或者模型承诺工具不存在的字段，因此我把一般规则应用、待核实条件和工具能力边界写进共享回答约束与工具说明，再用冻结的旧源码和新增题做对照。只对非常明确的问候和纯订单查询跳过证据判断，其余保持语义核对。

业务执行由程序校验。加急先暂停等待客服批准，批准前复查订单；事务与唯一约束防止重复创建工单。模型的批准文字不能代替审批。

评测是内部小样本，我分别报告证据覆盖、回答问题、工具边界、调用数和耗时，保留失败、退化及模型裁判误判，不把命中率或同模型裁判正确率当真实业务准确率。”

## 面试可能追问

| 问题 | 回答要点 |
| --- | --- |
| 为什么不直接提高TopK？ | 手机全库重排仍可能很低，金卡与券需要同时覆盖限定条款；补同源是面向短政策切分的证据组装选择，有预算代价和适用边界。 |
| 为什么不直接去掉检查器？ | 条件更正与证据复用需要核对最新语义。只跳过完整匹配的明确场景，不用宽泛关键词代替语义判断。 |
| 为什么不加第二个裁判兜底？ | 会增加调用、延迟并可能继承同源错误。先改同一次生成的输入、字段说明与可验证的业务校验。 |
| 怎么保证模型绝不编造？ | 不能凭提示保证。来源引用、工具证据和测试降低风险；审批资格、事务与去重由程序保证，语义正确性仍需评估和人工渠道。 |
| 现在可以生产上线吗？ | 适合本地演示与求职说明；没有真实仓库/退款/开票集成，能力和评测边界需如实说明。 |

独立人工盲审仍需真人逐条确认，可直接使用docs/prior-evaluation-review.md中的8题清单。本助手的复核不记作真人签字。

## MCP 补充演示

运行 `scripts/verify_mcp_tools.py`，展示原生 SDK 客户端发现两项只读工具，并对照真实订单和政策结果。说明 Agent 作为客户端消费自己暴露的工具，LangGraph 负责流程；MCP 负责工具协议，两者可以共存。审批写入不暴露到 MCP。

新增工作可以讲为：抽出共用业务逻辑，封装只读 Server，接入官方适配器，维护持久会话并保证绑定与执行工具一致；通过真实调用发现 Windows 数值库延迟导入阻塞，调整到主线程预热。代价是一个子进程、启动预热和协议开销，收益是工具可被独立客户端复用。实际数据和限制见 [MCP 文档](mcp-tools.md)。
