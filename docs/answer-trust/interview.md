# 回答可信度：面试讲解提纲

## 一分钟介绍

CommerceDesk 原有混合检索、同源补证、多轮证据检查和人工审批。已有实验发现，检索到证据仍可能答错：例如混淆政策适用范围、强化“不承诺”的语气，或承诺查询订单工具没有的字段。

这次升级把最终回答拆成可校验的结论与证据关联，先检查引用和工具结果，再用一次模型检查政策适用性。工具进度仍可见，最终答案在检查完成后发布；失败时明确说明无法可靠确认，不无限重试。

我比较原基线、仅程序约束、程序约束加语义检查三个版本，分别测固定证据下的回答能力和MCP完整流程。除了错误，还统计任务完成度、误拒答、费用和等待时间。最终结论以已完成的实验和作者匿名复核为准，不能由离线测试数推导模型准确率。

## 五分钟演示顺序

1. 展示一个含虚构引用的候选答案，说明程序为什么拒绝发布。
2. 展示正常问题如何关联真实政策片段并发布答案；区分程序校验和模型语义检查。
3. 展示证据不足或审查故障时的保守结果；若之前已登记催单，仍显示真实登记状态。
4. 打开同场景的匿名对照与原始轨迹，解释一次改进或退化，以及新增用量和延迟。

离线脚本中的模型替身只用于演示机制，不是模型效果证据。现场真实模型演示要提前配置接口，并计入模型费用；保存的记录必须标明历史运行。

## 容易追问的技术问题

**引用存在为什么仍不够？** 存在性只能防虚构来源；相关片段可能不适用于该商品、会员等级或当前条件。充分支持结论仍需要语义判断和人工复核。

**模型检查模型是否可靠？** 检查器也会漏判和误拦，因此没有把检查器输出当评测真值。程序硬约束与语义判断分开，人工复核匿名结果，记录误拒答和任务完成度。

**为什么不反复重试修复？** 本轮首先验证一次检查的贡献，并限制额外调用。多次修复会扩大成本和分析范围；失败后的任务可用性是本轮必须报告的代价。

**为什么最终答案不逐字显示？** 已显示的错误无法可靠撤回。内部草稿必须与公开消息分开，且所有输出通道一致遵守发布边界，不能只在网页上隐藏。

**审批与回答检查如何分工？** 审批资格、事务和幂等仍由原业务代码控制。回答检查不授权业务操作，也不回滚已经执行的操作；公开结果必须如实反映真实状态。

**怎样避免测试集被调参污染？** 旧题全部作为回归集，新场景按家族分组；最终集在候选冻结后揭盲。一旦根据最终题修改系统，它就不再是未见测试。

**能否声称线上准确率提高？** 不能。这里使用合成场景和演示数据，作者参与复核；结论只能覆盖实际测试过的版本、场景、模型与配置。

## 成果表述规则

可以描述已实现的机制、实际通过的测试、已完成的对照及其成本。实验尚待人工复核时明确写“待复核”；默认开关保持关闭。只有满足预注册启用条件后，才能说明本次冻结测试中观察到的改进，不能把候选功能完成写成质量提升。
